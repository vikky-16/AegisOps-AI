## 3. Detailed Investigation of Potential Unfair Advantages

### 3.1 Is Strategy A (One-Shot) a Strawman?
- **Reviewer Concern:** *"Is One-Shot an artificially weak strawman? In real systems, wouldn't an SRE retry if a command failed?"*
- **Audit Finding:**  
  No. Strategy A represents **the dominant paradigm in production IT automation today** (e.g., standard Ansible, Terraform, SaltStack, and Kubernetes Job execution). In standard runbook automation, scripts execute commands sequentially and declare completion if the shell exit code is $0$. The core vulnerability identified by AegisOps AI is that **a command exit code of $0$ does not equal operational health restoration**. For example, in `memory_pressure`, restarting a container completes with exit code $0$, but if the memory leak is in an active request decompressor cache, memory saturation immediately returns upon traffic resumption. Strategy A is an authentic, highly realistic baseline representing standard industrial practice.

### 3.2 Is Strategy B (Validation-Only) a Strawman?
- **Reviewer Concern:** *"Why evaluate Validation-Only if it has the same attempt budget as One-Shot?"*
- **Audit Finding:**  
  Strategy B isolates the effect of **the independent validation oracle** from the effect of **iterative refinement**. It proves a vital scientific truth: **validation alone does NOT increase recovery rate ($\text{RSR} = 25\%$ across both)**; its sole function is to eliminate false recovery declarations ($\text{FRR}: 75\% \to 0\%$). The $+62.5\%$ gain in recovery success is driven entirely by the iterative refinement loop in Strategy C. Evaluating Strategy B is an indispensable scientific control that prevents confounding validation with refinement.

### 3.3 Does Strategy C Win Purely Because It Gets 3 Tries?
- **Reviewer Concern:** *"If Strategy C gets up to 3 attempts while Strategy A gets 1, isn't the comparison fundamentally unfair?"*
- **Audit Finding & Statistical Correction:**  
  This is a critical distinction that must be transparently addressed in the paper:
  1. Strategy C does consume more attempts ($\text{ARA} = 1.875$ vs $1.000$). This cost is explicitly documented as the overhead trade-off in Hypothesis H4.
  2. However, **blind retries without evidence-guided refinement do NOT achieve 87.5% recovery**. If a system blindly repeats the same failed action three times (e.g., rebooting a service with a corrupted configuration string, or repeatedly clearing cache for a thread pool leak), it achieves $0\%$ additional recovery while wasting $3\times$ the time.
  3. The $+62.5\%$ improvement is achieved because Strategy C's refinement algorithm **actively penalizes the failed action category and promotes orthogonal remedies** based on post-execution telemetry deltas.

## 4. Methodological Invariants to Preserve in the Paper

1. Always report Average Recovery Attempts ($\text{ARA}$) alongside Recovery Success Rate ($\text{RSR}$) to show the cost of closed-loop refinement.
2. Formulate the research claim as: *"Evidence-guided closed-loop refinement increases recovery correctness from 25.0% to 87.5% while eliminating false recovery declarations, at the cost of an average 0.875 additional attempts per incident."*
3. Never claim that Strategy C is "free" or that it achieves superior results with identical computational resources.
